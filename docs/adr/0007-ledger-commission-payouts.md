# ADR-0007: Деньги — журнал проводок, комиссия, удержание, выплаты

**Статус:** Принято · **Дата:** 2026-10-22 · **Ревизия:** 2

## Контекст

В маркетплейсе (ТЗ, 3.5) покупатель платит площадке, а площадка должна продавцу сумму под-заказа за вычетом комиссии. Деньги продавцу становятся доступны только после доставки и окончания срока удержания, потом он их выводит.

Требования:

1. **Ни одна сумма не теряется и не удваивается** при повторной доставке сообщений, ретраях и гонках.
2. **Баланс объясним:** любую сумму можно разложить на операции, из которых она сложилась.
3. **История неизменна:** ошибки исправляются новыми записями, а не правкой старых.
4. **Двойная выплата невозможна,** даже при одновременных запросах.

Суммы — целые числа в тийинах, тип `bigint` (ТЗ, раздел 5). Валюта одна — UZS.

## Рассмотренные варианты

| Вариант                       | Плюсы                                                                                                          | Минусы                                                                                                                |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Поле «баланс» у продавца      | Просто                                                                                                         | Нельзя объяснить, откуда сумма; повторная доставка события или гонка тихо портят деньги; исправление стирает историю  |
| Журнал в erp (как в ТЗ 0.0.1) | Продавец видит деньги рядом со складом                                                                         | Деньги в двух сервисах: списание и возврат — в payment, долг продавцу — в erp. Согласовывать их пришлось бы событиями |
| Отдельный сервис billing      | Чистая граница «деньги»                                                                                        | Девятый сервис; списание у провайдера и проводки окажутся в разных базах — снова распределённая согласованность       |
| **Журнал в payment**          | Все движения денег — локальные транзакции одной базы: операция у провайдера и её проводки фиксируются атомарно | payment растёт: платежи, проводки, выплаты, ставки комиссии                                                           |

Выбрано: **журнал проводок по двойной записи в payment.** erp ведёт реестр продаж — учётные документы продавца, но не деньги.

## Решение

### 1. Границы

| Что                                                     | Где                                         |
| ------------------------------------------------------- | ------------------------------------------- |
| Авторизация, списание, отмена, возврат денег покупателя | payment (ADR-0005)                          |
| Журнал проводок, балансы продавцов, удержание           | payment                                     |
| Ставки комиссии                                         | payment; редактирует админ через API        |
| Выплаты продавцам                                       | payment                                     |
| Реестр продаж (что, кому и когда продано)               | erp                                         |
| Финансы в кабинете продавца                             | backoffice читает API payment через gateway |

### 2. Счета

| Счёт                          | Тип           | Смысл                                                           |
| ----------------------------- | ------------- | --------------------------------------------------------------- |
| `cash:psp`                    | актив         | Деньги площадки у платёжного провайдера                         |
| `seller:{sellerId}:pending`   | обязательство | Долг продавцу, пока не прошёл срок удержания                    |
| `seller:{sellerId}:available` | обязательство | Долг продавцу, доступный к выплате                              |
| `commission:deferred`         | обязательство | Комиссия, которая ещё может вернуться покупателю при отмене     |
| `commission:revenue`          | доход         | Заработанная комиссия площадки                                  |
| `refunds:in-transit`          | обязательство | Возврат покупателю запрошен у провайдера, но ещё не подтверждён |
| `payouts:in-transit`          | обязательство | Выплата продавцу отправлена провайдеру, но ещё не подтверждена  |

### 3. Операции и проводки

Обозначения: `S` — сумма под-заказа, `C` — комиссия по нему, `X` — сумма выплаты.

| №   | Операция                                          | Источник                                | Дебет                   | Кредит                  | Сумма   |
| --- | ------------------------------------------------- | --------------------------------------- | ----------------------- | ----------------------- | ------- |
| 1   | Деньги покупателя списаны — по каждому под-заказу | `CapturePayment` (ADR-0005)             | `cash:psp`              | `seller:{id}:pending`   | `S − C` |
|     |                                                   |                                         | `cash:psp`              | `commission:deferred`   | `C`     |
| 2   | Срок удержания после доставки истёк               | Планировщик после `sub-order.delivered` | `seller:{id}:pending`   | `seller:{id}:available` | `S − C` |
|     |                                                   |                                         | `commission:deferred`   | `commission:revenue`    | `C`     |
| 3   | Под-заказ отменён, возврат запрошен               | `RefundPayment` (ADR-0005)              | `seller:{id}:pending`   | `refunds:in-transit`    | `S − C` |
|     |                                                   |                                         | `commission:deferred`   | `refunds:in-transit`    | `C`     |
| 4   | Возврат подтверждён провайдером                   | Webhook                                 | `refunds:in-transit`    | `cash:psp`              | `S`     |
| 5   | Продавец запросил выплату                         | API кабинета                            | `seller:{id}:available` | `payouts:in-transit`    | `X`     |
| 6   | Выплата подтверждена                              | Webhook                                 | `payouts:in-transit`    | `cash:psp`              | `X`     |
| 7   | Выплата не прошла                                 | Webhook                                 | `payouts:in-transit`    | `seller:{id}:available` | `X`     |

- В каждой операции дебет равен кредиту.
- Снятие авторизации (`CancelPayment`) проводок не создаёт: деньги не двигались.
- Отмена возможна только до отгрузки, а удержание начинается только после доставки. Поэтому в момент отмены долг продавцу всегда лежит на `pending`.
- Возвраты после доставки (после MVP) будут списывать с `available`, а если там не хватает — уводить баланс продавца в минус. Это решается отдельным ADR.

### 4. Комиссия

- Ставка задаётся в базисных пунктах (1 б. п. = 0,01%) на категорию; ставка по умолчанию хранится под ключом `*`.
- `CapturePayment` передаёт для каждой позиции путь категории от корня до листа (`categoryPath`). Применяется ставка самой глубокой категории пути, для которой она задана, иначе — ставка по умолчанию.
- Комиссия считается по каждой позиции и округляется вниз до тийина: `commission = floor(amountMinor × rateBp / 10 000)`. Остаток от округления достаётся продавцу. Комиссия под-заказа — сумма по его позициям.
- Ставка фиксируется в момент списания денег. Изменение ставки не меняет уже списанные заказы.
- Категориями владеет catalog. payment держит read-model категорий по событиям `category.*` (`catalog.events`), поэтому API ставок отклоняет `category_id`, которого нет. Ставка по умолчанию `*` — исключение.
- Деньги считаются только целыми числами. Схема `Money` и арифметика — в `libs/contracts/src/money.ts` (ADR-0003).

```sql
CREATE TABLE commission_rates (
  category_id text        PRIMARY KEY,   -- '*' — ставка по умолчанию
  rate_bp     int         NOT NULL CHECK (rate_bp BETWEEN 0 AND 10000),
  updated_at  timestamptz NOT NULL DEFAULT now()
);
```

### 5. Расчёты по под-заказам и удержание

```sql
CREATE TABLE settlements (
  sub_order_id     text        PRIMARY KEY,
  order_id         text        NOT NULL,
  seller_id        text        NOT NULL,
  gross_minor      bigint      NOT NULL,   -- S
  commission_minor bigint      NOT NULL,   -- C
  status           text        NOT NULL,   -- PENDING, HOLD, AVAILABLE, REFUNDED
  release_at       timestamptz
);

CREATE TABLE settlement_lines (
  sub_order_id     text   NOT NULL REFERENCES settlements (sub_order_id),
  sku_id           text   NOT NULL,
  amount_minor     bigint NOT NULL,
  rate_bp          int    NOT NULL,   -- ставка на момент списания
  commission_minor bigint NOT NULL,
  PRIMARY KEY (sub_order_id, sku_id)
);
```

| Статус      | Когда                                                                    | Проводка |
| ----------- | ------------------------------------------------------------------------ | -------- |
| `PENDING`   | Деньги покупателя списаны                                                | 1        |
| `HOLD`      | Пришёл `sub-order.delivered`: `release_at = occurredAt + срок удержания` | —        |
| `AVAILABLE` | Планировщик: `release_at` наступил                                       | 2        |
| `REFUNDED`  | Под-заказ отменён до отгрузки                                            | 3        |

- Срок удержания — настройка `SELLER_HOLD_DAYS`, по умолчанию 7 дней (ТЗ, раздел 10); в тестах — секунды.
- `release_at` считается от `occurredAt` события, а не от `now()`: при replay или задержке потребителя результат тот же.
- Планировщик выбирает созревшие расчёты через `FOR UPDATE SKIP LOCKED`, так же как в ADR-0005 (п. 6).

### 6. Выплаты

1. Продавец запрашивает выплату (право `finance`, ADR-0006).
2. В одной транзакции payment:
   - блокирует строку баланса `seller:{id}:available` (`SELECT … FOR UPDATE`);
   - проверяет, что доступно не меньше `X` и что `X` не меньше минимальной суммы выплаты;
   - создаёт выплату со статусом `REQUESTED` и проводку 5.
3. Фоновый обработчик отправляет выплату в `fake-psp` с ключом идемпотентности `payoutId`. Внешний вызов делается после коммита, а не внутри транзакции.
4. Webhook провайдера: успех → проводка 6, статус `PAID`, событие `payout.paid`; отказ → проводка 7, статус `FAILED`, событие `payout.failed`.

Блокировка строки баланса сериализует одновременные запросы: второй запрос увидит уже уменьшенный баланс. Строки балансов в одной транзакции всегда блокируются в порядке сортировки имени счёта, чтобы не было deadlock.

### 7. Хранение и инварианты

```sql
CREATE TABLE ledger_transactions (
  id         uuid        PRIMARY KEY,
  kind       text        NOT NULL,   -- capture, hold_release, refund_requested, refund_completed,
                                     -- payout_requested, payout_paid, payout_failed
  source_id  text        NOT NULL,   -- orderId, subOrderId, refundId или payoutId
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (kind, source_id)           -- одна проводка на операцию: повтор не удваивает деньги
);

CREATE TABLE ledger_entries (
  id             bigserial PRIMARY KEY,
  transaction_id uuid      NOT NULL REFERENCES ledger_transactions (id),
  account        text      NOT NULL,
  amount_minor   bigint    NOT NULL CHECK (amount_minor <> 0),   -- дебет > 0, кредит < 0
  seller_id      text,
  sub_order_id   text
);

CREATE TABLE account_balances (
  account       text   PRIMARY KEY,
  balance_minor bigint NOT NULL DEFAULT 0   -- сумма записей счёта; долг продавцу = −balance_minor
);
```

- Проводка, её записи и изменение `account_balances` — одна транзакция вместе с операцией-источником.
- **Сумма записей проводки = 0** — проверяет база при коммите:

  ```sql
  CREATE FUNCTION ledger_check_balanced() RETURNS trigger AS $$
  DECLARE
    tx_id uuid;
    total bigint;
    cnt   int;
  BEGIN
    IF TG_TABLE_NAME = 'ledger_transactions' THEN
      tx_id := NEW.id;
    ELSE
      tx_id := NEW.transaction_id;
    END IF;

    SELECT COALESCE(SUM(amount_minor), 0), COUNT(*) INTO total, cnt
    FROM ledger_entries WHERE transaction_id = tx_id;

    IF cnt < 2 OR total <> 0 THEN
      RAISE EXCEPTION 'ledger transaction % is not balanced (entries: %, sum: %)', tx_id, cnt, total;
    END IF;
    RETURN NULL;
  END $$ LANGUAGE plpgsql;

  -- проводка без записей: SUM по пустому набору = NULL, и проверка только по записям её бы пропустила
  CREATE CONSTRAINT TRIGGER ledger_transaction_balanced
    AFTER INSERT ON ledger_transactions
    DEFERRABLE INITIALLY DEFERRED
    FOR EACH ROW EXECUTE FUNCTION ledger_check_balanced();

  -- запись, дописанная позже к уже существующей проводке
  CREATE CONSTRAINT TRIGGER ledger_entry_balanced
    AFTER INSERT ON ledger_entries
    DEFERRABLE INITIALLY DEFERRED
    FOR EACH ROW EXECUTE FUNCTION ledger_check_balanced();
  ```

  Проверка срабатывает при коммите. Проводка без записей, с одной записью или с ненулевой суммой не коммитится.

- **Журнал только дополняется** — изменить или удалить запись нельзя:

  ```sql
  CREATE FUNCTION ledger_append_only() RETURNS trigger AS $$
  BEGIN
    RAISE EXCEPTION 'ledger is append-only';
  END $$ LANGUAGE plpgsql;

  CREATE TRIGGER ledger_entries_append_only
    BEFORE UPDATE OR DELETE ON ledger_entries
    FOR EACH ROW EXECUTE FUNCTION ledger_append_only();

  CREATE TRIGGER ledger_transactions_append_only
    BEFORE UPDATE OR DELETE ON ledger_transactions
    FOR EACH ROW EXECUTE FUNCTION ledger_append_only();
  ```

- **Ежедневная сверка** (фоновая задача, расхождение — алерт):
  - сумма всех записей журнала = 0;
  - `account_balances` = сумма записей по каждому счёту;
  - `seller:{id}:pending` = сумма `S − C` по расчётам продавца в статусах `PENDING` и `HOLD`;
  - доступный баланс продавца не меньше нуля.

### 8. Отчёты

- **Продавцу:** баланс в ожидании и доступный, история операций (записи журнала по его счетам с привязкой к под-заказам), выплаты.
- **Админу:** заработанная и отложенная комиссия за период, выплаты, возвраты.
- **Сверка с erp** (критерий этапа 4, ТЗ): сумма `S` по расчётам продавца совпадает с суммой продаж в реестре erp за вычетом сторно.

### 9. Тестирование

- **Unit:** расчёт комиссии и округление; каждая операция из п. 3 даёт сбалансированную проводку.
- **Property-based** (например, fast-check): случайная последовательность операций — списание, отмена, доставка, удержание, выплата, успех и отказ выплаты — сохраняет все инварианты из п. 7.
- **Интеграционные** (настоящий Postgres):
  - повторный `CapturePayment` не создаёт вторую проводку;
  - два одновременных запроса выплаты на весь баланс — проходит один;
  - `UPDATE` записи журнала отклоняется базой;
  - несбалансированная проводка не коммитится, проводка без записей — тоже.

## Последствия

**Плюсы**

- Любой баланс раскладывается на операции; история неизменна.
- Повторы и гонки не портят деньги: уникальность проводки на операцию и блокировки балансов.
- Деньги в одном сервисе: никакой распределённой согласованности внутри денежной логики.

**Минусы и цена**

- payment становится самым сложным сервисом.
- Двойная запись непривычна; ошибка в выборе счёта ловится только тестами и сверкой.
- Продавец видит деньги в кабинете через API payment, а продажи — через API erp: это два источника, поэтому нужна сверка.
- **Горячие строки.** Каждое списание обновляет одни и те же строки `account_balances`: `cash:psp` и `commission:deferred`. Поэтому все списания площадки сериализуются на этих двух блокировках. Для MVP это приемлемо. На этапе hardening измеряем нагрузочным тестом и, если нужно, либо не храним `account_balances` для платформенных счетов (баланс считается по журналу), либо шардируем счёт: `cash:psp:{0..N}`, где баланс равен сумме шардов.

**Правила для code review**

- изменение баланса без проводки;
- `UPDATE` или `DELETE` в журнале;
- деньги во `float`, `number` с дробной частью или `Decimal` вместо целых тийинов;
- запрос выплаты без блокировки строки баланса;
- внешний вызов провайдера внутри транзакции базы.

## Открытые вопросы

- Минимальная сумма выплаты (ТЗ, раздел 10).
- Отрицательный баланс продавца при возвратах после доставки — после MVP.
- Сверка с отчётами провайдера — после MVP.
