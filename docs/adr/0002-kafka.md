# ADR-0002: Kafka как брокер доменных событий

**Статус:** Принято · **Дата:** 2026-10-22 · **Ревизия:** 5

## Контекст

Сервисам (Payments, ERP, CRM, …) нужна асинхронная шина доменных событий со следующими требованиями:

1. **Асинхронность.** Сервис-источник не ждёт, пока потребители обработают событие.
2. **Порядок внутри агрегата.** События одной сущности обрабатываются в порядке возникновения: `payment.created → payment.authorized → payment.captured → payment.refunded`.
3. **Replay всей истории.** Можно перечитать события с самого начала, например пересчитать сегменты CRM после изменения логики.
4. **Независимые потребители.** Одно событие (`order.confirmed`) читают ERP и CRM, не мешая друг другу.
5. **Команды saga.** Оркестратор оформления заказа отправляет участникам команды и получает ответы событиями (ADR-0005).

## Рассмотренные варианты

|                         | RabbitMQ                                     | **Kafka**                                             |
| ----------------------- | -------------------------------------------- | ----------------------------------------------------- |
| Модель                  | Очереди, push; сообщение удаляется после ack | Лог, pull; сообщения хранятся по retention            |
| Replay                  | Только через RabbitMQ Streams (3.9+)         | Штатно: сдвиг offset                                  |
| Порядок                 | В очереди при одном consumer                 | В партиции; партицию задаёт ключ                      |
| Независимые потребители | Отдельная очередь на каждого через exchange  | Отдельный consumer group на каждого, один топик       |
| Локальный запуск        | Один контейнер                               | Один контейнер (с 4.0 только KRaft, ZooKeeper удалён) |
| Сложность эксплуатации  | Ниже                                         | Выше: партиции, offset, lag, retention                |
| Экосистема              | Широкая                                      | Отраслевой стандарт для event streaming               |

RabbitMQ Streams закрывают replay, но инструменты и практики вокруг Kafka шире. Дополнительный аргумент: опыт с Kafka востребован на рынке. Для этого проекта это осознанная часть решения, а не техническая необходимость.

## Решение

### 1. Брокер

- Apache Kafka 4.x в режиме KRaft.
- Локально: один узел (broker + controller), `replication.factor=1`.
- Прод (если будет): от 3 брокеров, `replication.factor=3`, `min.insync.replicas=2`.
- `auto.create.topics.enable=false`. Топики создаёт init-скрипт с явными параметрами.

### 2. Клиент

- Собственный адаптер `libs/kafka` с интерфейсами `EventPublisher` и `EventHandler`. Сервисы не импортируют клиент Kafka напрямую.
- Реализация: `kafkajs` (чистый JS, без нативной сборки).
- NestJS microservices Kafka transport напрямую не используем. Адаптер даёт единый контроль над конвертом события, ретраями и DLQ во всех сервисах. Обработчики при этом оформляются как обычные Nest-провайдеры.
- Почему адаптер: у kafkajs нет активной разработки с середины 2024 года. При необходимости реализация меняется на `@confluentinc/kafka-javascript` (KafkaJS-совместимый API поверх librdkafka) без изменений в сервисах.

### 3. Топики

| Топик                                                | Назначение                                                 | Партиции | Retention        |
| ---------------------------------------------------- | ---------------------------------------------------------- | -------- | ---------------- |
| `<context>.events` (например, `payment.events`)      | Доменные события контекста                                 | 6        | `-1` (бессрочно) |
| `<context>.commands` (например, `erp.commands`)      | Команды saga сервису-владельцу (ADR-0005)                  | 6        | 7 дней           |
| `<consumer-group>.dlq` (например, `crm-service.dlq`) | Сообщения, которые эта consumer group не смогла обработать | 1        | `-1` (бессрочно) |

- **Один топик событий на bounded context.** Все типы событий агрегата лежат в одном топике. Если разнести типы по разным топикам, порядок между ними не гарантирован.
- **Топик команд читает только сервис-владелец.** Команды не перечитываются при replay: повторное выполнение команды — новое действие, а не пересчёт проекции. Поэтому срок хранения команд ограничен — его хватает для разбора инцидентов.
- **Топик создаётся, когда у него появляется потребитель.** Текущий список топиков — SD-00, раздел 3.
- **Число партиций фиксируется при создании.** Его увеличение меняет `hash(key) % N`, и новые события агрегата уходят в другую партицию, пока старые ещё не обработаны. Поэтому меняем только через миграцию в новый топик. 6 — стартовое значение, оно же максимум параллельных инстансов одного потребителя на топик.
- **Бессрочное хранение событий нужно для replay.** Значение Kafka по умолчанию (7 дней) требование replay не выполняет. Размер топиков мониторим и пересматриваем при росте (tiered storage, снапшоты).
- **Отдельных retry-топиков нет:** они ломают порядок (см. п. 8).

### 4. Ключ партиции

**Ключ = идентификатор сущности, состояние которой меняют события.** По умолчанию это `aggregateId`.

Если события _разных_ агрегатов меняют общее состояние (баланс клиента, складской остаток), ключом для этого потока становится id общего состояния (`customerId`, `skuId`). Более крупный ключ сохраняет и порядок внутри агрегата: все платежи клиента окажутся в одной партиции. Такие исключения фиксируются отдельным ADR.

Порядок между разными ключами не гарантируется и не нужен.

В одном топике могут быть события с разными ключами. Например, в `erp.events` ответ saga `stock.reserved` относится к резерву заказа (ключ `orderId`), а `stock.level-changed` — к остатку товара (ключ `skuId`).

**Команды saga** — ключ `orderId`. Все команды одного заказа лежат в одной партиции, поэтому компенсация (`ReleaseStock`) всегда обрабатывается после команды, которую она отменяет (`ReserveStock`).

### 5. Конверт сообщения

События и команды публикуются в едином формате (JSON). Zod-схема конверта — `libs/contracts/src/envelope.ts` (ADR-0003).

```jsonc
{
  "eventId": "0192b4c6-7a1e-7c3d-9f00-3b5e2a1d4c88", // UUID v7, ключ идемпотентности
  "type": "payment.captured",
  "version": 1, // версия схемы payload
  "aggregateType": "payment",
  "aggregateId": "pay_123",
  "aggregateVersion": 2, // порядковый номер события агрегата
  "occurredAt": "2026-10-22T10:00:00Z",
  "correlationId": "req_abc", // один на всю цепочку, начиная с HTTP-запроса
  "causationId": "0192b4c6-6f00-7a2b-8c11-5d3e9a0b7f21", // eventId сообщения, вызвавшего это; null у первого
  "payload": {},
}
```

Имена (`type`):

- событие — `сущность.действие` в прошедшем времени: `stock.reserved`;
- команда — PascalCase в повелительном наклонении: `ReserveStock`.

У команд поля `aggregate*` относятся к агрегату, ради которого команда отправлена: для saga — к заказу.

Правила версионирования:

- Добавление необязательных полей — без смены `version`.
- Удаление, переименование или смена типа поля — новый `version`. Потребители поддерживают старую и новую версии на время миграции.
- `aggregateVersion` позволяет потребителю заметить пропуск или перестановку событий агрегата.

### 6. Публикация: transactional outbox

Проблема: запись в БД и отправка в Kafka — две отдельные операции. Если сервис упадёт между ними, событие потеряется, и потребители никогда о нём не узнают.

- Событие пишется в таблицу `outbox` **в той же транзакции**, что и изменение агрегата.
- Relay читает неотправленные записи, публикует их в Kafka и помечает отправленными.
- Один активный relay на сервис (лидерство через `pg_advisory_lock` на выделенном соединении), чтение `ORDER BY id`.
- Изменения одного агрегата сериализуются (optimistic locking по `aggregateVersion` или блокировка строки). Поэтому порядок событий агрегата в `outbox` совпадает с порядком их возникновения.
- Relay может отправить событие повторно (упал после отправки, до пометки). Это допустимо: потребители идемпотентны (п. 7).

```sql
CREATE TABLE outbox (
  id            bigserial   PRIMARY KEY,
  event_id      uuid        NOT NULL UNIQUE,
  topic         text        NOT NULL,
  message_key   text        NOT NULL,
  payload       jsonb       NOT NULL,              -- конверт целиком
  headers       jsonb       NOT NULL DEFAULT '{}', -- traceparent для заголовков Kafka
  created_at    timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz
);

CREATE INDEX outbox_unpublished ON outbox (published_at, id); -- не частичный: Prisma-схема его не выражает (SD-01, п. 6)
```

Настройки producer (защита от перестановки и дублей при ретраях):

```ts
kafka.producer({
  idempotent: true, // в kafkajs помечено как experimental
  maxInFlightRequests: 1, // строгий порядок при ретраях
}); // acks: -1 (all) — значение по умолчанию в send()
```

### 7. Потребление

- `groupId` = имя сервиса: `erp-service`, `crm-service`. Каждая группа читает все события и хранит свой offset.
- Внутри партиции события обрабатываются строго по одному (`eachMessage`). Разные партиции — параллельно (`partitionsConsumedConcurrently`).
- **Запрещено** обрабатывать сообщения одной партиции параллельно (например, `Promise.all` по батчу).
- Доставка at-least-once, поэтому каждый обработчик идемпотентен:

```sql
CREATE TABLE processed_events (
  handler      text        NOT NULL,
  event_id     uuid        NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (handler, event_id)
);
```

- Ключ включает `handler`: в одном сервисе на событие может быть несколько обработчиков (в crm на `order.confirmed` — LTV и таймлайн). С ключом только по `event_id` второй обработчик принял бы событие за дубль и молча его пропустил.
- В одной транзакции с изменением данных выполняется `INSERT … ON CONFLICT DO NOTHING`. Если вставлено 0 строк — это дубль, событие пропускается.
- Offset коммитится только после успешной транзакции.
- **Очистка `processed_events`:** фоновая задача удаляет строки старше 30 дней. Дубль может прийти от ретрая producer, повтора relay или перебалансировки группы: это минуты, а не недели. Повторная обработка из DLQ или replay старше 30 дней защищена проверкой `aggregateVersion` (ADR-0004, п. 3) или идёт в новые таблицы (п. 9).
- Внешние побочные эффекты (письма, HTTP-вызовы) выполняются с ключом идемпотентности `eventId`, если внешний сервис его поддерживает.

### 8. Ошибки, ретраи, DLQ

- **Временные ошибки** (БД недоступна, таймаут): ретрай внутри обработчика, 5 попыток, экспоненциальная пауза от 1 с. Между попытками вызывается `heartbeat()`, чтобы потребитель не выпал из группы. Партиция на это время останавливается — осознанно, ради порядка. Остальные партиции продолжают работать.
- **Постоянные ошибки** (невалидный payload, неизвестная версия) и исчерпанные ретраи: сообщение уходит в DLQ своей consumer group — `<consumer-group>.dlq` — с исходным ключом и заголовками `x-original-topic`, `x-original-partition`, `x-original-offset`, `x-consumer-group`, `x-handler`, `x-error`, `x-attempts`.
- **DLQ пишется напрямую producer'ом, мимо outbox:** это не доменное событие, связывать его с изменением в БД не нужно. Если отправка в DLQ не удалась, offset не коммитится. DLQ-топики декларируются вместе с остальными: автосоздание выключено (п. 1).
- **Перебалансировка во время ретраев** не считается ошибкой: ретраи прерываются без DLQ, сообщение получит новый владелец партиции.
- **Почему DLQ на consumer group, а не на топик.** Если вернуть сообщение в исходный топик, его заново получат все группы, хотя сломалась одна. Идемпотентность защитит от двойной обработки, но это лишняя нагрузка и шум в логах.
- **Повторная обработка:** после исправления запускается служебная команда сервиса `dlq-reprocess`. Она читает DLQ своей группы и вызывает тот же обработчик с теми же проверками `processed_events` и `aggregateVersion`. Другие consumer groups сообщение повторно не получают. Сообщение обрабатывается позже более новых событий агрегата, поэтому проверка `aggregateVersion` обязательна.
- **Команды saga** в DLQ — не единственная страховка: оркестратор заметит отсутствие ответа по дедлайну (ADR-0005, п. 6).

**Известное ограничение.** Если событие агрегата ушло в DLQ, следующие события этого агрегата обрабатываются дальше, и порядок для этого агрегата нарушается. Сейчас мы это принимаем: потребитель логирует расхождение `aggregateVersion`. Доработка описана в разделе «Потом».

### 9. Replay

- Применяется только к **проекциям** (read-модели, сегменты, отчёты) и только к топикам **событий**; топики команд не перечитываются. Побочные эффекты (письма, внешние вызовы) при replay отключаются флагом.
- Обработчики детерминированы: время берётся из `occurredAt`, а не из `now()`.
- Процедура:
  1. Новый consumer group (например, `crm-segments-rebuild-2026-11`) с `fromBeginning: true` строит проекцию в новых таблицах.
  2. Когда группа догнала конец топика (lag около 0), чтение переключается на новые таблицы.
  3. Старые таблицы и группа удаляются.
- Для простых случаев: остановить сервис, очистить проекцию и её строки в `processed_events`, сбросить offset группы на начало (`kafka-consumer-groups.sh --reset-offsets --to-earliest`).

### 10. Локальная инфраструктура

- docker-compose:
  - `apache/kafka` с зафиксированной версией 4.x;
  - `ghcr.io/kafbat/kafka-ui` для отладки (форк provectus/kafka-ui, развитие которого остановлено).
- Init-скрипт создаёт топики с партициями и retention из п. 3.

## Последствия

**Плюсы**

- Новый потребитель подключается новым consumer group без изменений в сервисе-источнике.
- Replay всей истории для проекций.
- Порядок событий агрегата сохраняется при параллельной обработке разных агрегатов.

**Минусы и цена**

- Каждому сервису-источнику нужны `outbox` и relay, каждому потребителю — `processed_events`.
- Eventual consistency: ERP и CRM видят платёж с задержкой.
- Kafka сложнее RabbitMQ в эксплуатации: партиции, offset, lag, retention.
- Бессрочный retention увеличивает объём хранения.

**Правила для code review** — что ломает порядок или надёжность:

- публикация в Kafka в обход `outbox`;
- параллельная обработка сообщений одной партиции;
- изменение числа партиций существующего топика;
- ключ, отличный от id сущности, состояние которой меняет событие;
- retry-топики;
- обработчик без проверки `processed_events`;
- команда в топике событий или событие в топике команд;
- DLQ, общий для нескольких consumer groups.

## Сейчас и потом

**Сейчас (MVP шины):** пункты 1–10.

**Потом:**

- Schema Registry (JSON Schema или Avro) для автоматической проверки совместимости схем.
- Мониторинг consumer lag и размера топиков, алерты.
- «Парковка» агрегата: если событие ушло в DLQ, следующие события того же ключа тоже откладываются до разбора, и порядок не нарушается.
- CDC (Debezium) вместо polling relay, если нагрузка на `outbox` станет заметной.
- Переход на `@confluentinc/kafka-javascript`, если kafkajs начнёт мешать (баги, несовместимость с новыми версиями брокера).

## Открытые вопросы

- Есть ли в ERP потоки, где события разных платежей меняют общее состояние (баланс клиента, складские остатки)? Если да, ключ для них пересматривается (п. 4).
- Число партиций для каждого топика по ожидаемой нагрузке.

## Когда пересмотреть решение

- Объём хранения или стоимость инфраструктуры становятся проблемой.
- Эксплуатация Kafka обходится дороже пользы: мало событий, replay не используется.

## Связанные решения

- ADR-0003: схемы конверта, событий и команд в `libs/contracts`.
- ADR-0004: read-models и `processed_events` в базе сервиса.
- ADR-0005: checkout saga — команды и ответы.
- SD-00: каталог топиков и сообщений.
