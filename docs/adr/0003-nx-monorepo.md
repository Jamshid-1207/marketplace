# ADR-0003: Nx monorepo

**Статус:** Принято · **Дата:** 2026-10-22 · **Ревизия:** 4

## Контекст

8 NestJS-сервисов (ADR-0001) и 2 Next.js-приложения — витрина (`storefront`) и `backoffice` (кабинет продавца и админка платформы) — используют общие контракты событий и API. Если держать их в разных репозиториях, контракты начнут расходиться: изменение у producer'а ломает consumer'а, и это обнаруживается только в рантайме.

Разработчик один, поэтому накладные расходы на инфраструктуру репозиториев должны быть минимальными.

**Ограничение, которое важно понимать с самого начала:** монорепо ловит несовместимость контрактов при сборке, но не в рантайме (см. п. 5).

## Рассмотренные варианты

| Вариант                          | Плюсы                                                                                                                                                                              | Минусы                                                                                                                                                                |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Polyrepo                         | Настоящая независимость версий и деплоя                                                                                                                                            | Контракты публикуются как npm-пакеты с версиями. Изменение контракта = релиз пакета + обновление в N репозиториях. Для одного разработчика — чистые накладные расходы |
| pnpm workspaces без оркестратора | Минимум инструментов                                                                                                                                                               | Нет affected, кэша задач, генераторов и проверки границ — всё вручную скриптами                                                                                       |
| Turborepo                        | Лёгкий раннер задач поверх workspaces; `--affected`, кэш, `turbo boundaries` с тегами; меньше «магии»                                                                              | Нет официальных плагинов для NestJS: каркасы сервисов и задачи сборки настраиваются вручную                                                                           |
| **Nx**                           | Официальные плагины для Nest и Next (генераторы, задачи сборки); affected, кэш, граф проектов; зрелое правило границ через ESLint; локальные генераторы для своего шаблона сервиса | Больше конфигурации и неявного поведения; обновления через `nx migrate` могут требовать ручных правок; привязка к соглашениям плагинов                                |

Выбран Nx: для 8 однотипных Nest-сервисов генераторы, готовые задачи сборки и зрелая проверка границ экономят больше времени, чем стоит конфигурация Nx. Опыт с Nx — дополнительный, но не решающий аргумент.

## Решение

### 1. Инструменты и связывание проектов

- Nx + pnpm.
- Проекты связываются через **workspaces pnpm + TypeScript project references** — настройка по умолчанию для новых воркспейсов Nx 20+. Path aliases в `tsconfig.base.json` не используем. Переход между этими способами позже болезненный, поэтому решение фиксируется сразу.
- Внутренние пакеты подключаются явно через `"@repo/contracts": "workspace:*"` в `package.json` проекта. Зависимость между проектами видна в манифесте, а не только в импортах.
- Версии Nx и плагинов зафиксированы. Обновление — через `nx migrate`, отдельным коммитом.

### 2. Структура

```
apps/
  gateway/  auth/  catalog/  order/      # NestJS
  payment/  erp/   crm/      notification/
  storefront/                            # Next.js, витрина
  backoffice/                            # Next.js, кабинет продавца и админка платформы
libs/
  contracts/       # схемы событий, команд, API и денег: TS-типы + zod
  kafka/           # адаптер Kafka, конверт сообщения, DLQ (ADR-0002)
  outbox/          # таблица outbox и relay
  idempotency/     # processed_events, обёртка обработчика
  observability/   # логгер, OpenTelemetry, correlationId
  auth/            # проверка JWT по JWKS, область доступа, декоратор прав (ADR-0006)
tools/
  generators/      # шаблон сервиса (ADR-0001, п. 8) как локальный Nx-генератор
```

Правила:

- Библиотеки `common`, `shared`, `utils` запрещены. Каждая lib создаётся под конкретную задачу и называется по ней.
- Код выносится в lib, когда понадобился во втором проекте, а не заранее (ADR-0001).
- Новый сервис создаётся генератором: `nx g @repo/generators:service <name>`.
- Общие UI-компоненты storefront и backoffice — `libs/ui`, когда появится реальное дублирование.

### 3. Контракты

- `libs/contracts` зависит **только от `zod`**. Никаких NestJS, `class-validator`, `reflect-metadata`: иначе они попадут в бандлы Next.js.
- Каждый контракт — zod-схема и выведенный из неё тип.
- Бэкенд валидирует входящие данные этими же схемами (валидационный pipe в Nest), фронт — формы и ответы API.
- Структура:
  - `envelope.ts` — конверт сообщения (ADR-0002, п. 5);
  - `money.ts` — схема денег в тийинах и целочисленная арифметика (ADR-0007);
  - `events/<context>/<event>.v<N>.ts` — события;
  - `commands/<context>/<command>.v<N>.ts` — команды saga (ADR-0005);
  - `api/<service>/…` — публичные API.

```ts
// libs/contracts/src/events/payment/payment-captured.v1.ts
import { z } from "zod";

export const PaymentCapturedV1 = z.object({
  paymentId: z.string(),
  orderId: z.string(),
  amountMinor: z.number().int(),
  currency: z.string().length(3),
});

export type PaymentCapturedV1 = z.infer<typeof PaymentCapturedV1>;
```

### 4. Границы модулей

Каждый проект получает два тега: тип и платформу.

| Проект                                                         | Теги                                |
| -------------------------------------------------------------- | ----------------------------------- |
| Nest-сервисы в `apps/`                                         | `type:app`, `platform:node`         |
| `apps/storefront`, `apps/backoffice`                           | `type:app`, `platform:web`          |
| `libs/contracts`                                               | `type:contracts`, `platform:shared` |
| `libs/kafka`, `outbox`, `idempotency`, `observability`, `auth` | `type:infra`, `platform:node`       |
| `libs/ui` (когда появится)                                     | `type:ui`, `platform:web`           |

```js
// eslint.config.mjs
'@nx/enforce-module-boundaries': ['error', {
  depConstraints: [
    { sourceTag: 'type:app',       onlyDependOnLibsWithTags: ['type:contracts', 'type:infra', 'type:ui'] },
    { sourceTag: 'type:infra',     onlyDependOnLibsWithTags: ['type:contracts', 'type:infra'] },
    { sourceTag: 'type:ui',        onlyDependOnLibsWithTags: ['type:contracts', 'type:ui'] },
    { sourceTag: 'type:contracts', onlyDependOnLibsWithTags: [] },
    { sourceTag: 'platform:web',   onlyDependOnLibsWithTags: ['platform:web', 'platform:shared'] },
    { sourceTag: 'platform:node',  onlyDependOnLibsWithTags: ['platform:node', 'platform:shared'] },
  ],
}]
```

Если у проекта несколько тегов, должны выполняться все правила. Что это даёт:

- фронт не может импортировать `libs/kafka` (она `platform:node`) — Node-код не попадёт в браузерный бандл;
- контракты ни от чего не зависят;
- инфраструктурные libs не зависят от приложений и UI.

Нарушение границ — ошибка lint, CI падает.

### 5. Монорепо не отменяет версионирование контрактов

Монорепо гарантирует согласованность контрактов **при сборке**. В рантайме — нет:

- сервисы деплоятся не одновременно: старый consumer какое-то время получает события нового формата;
- в Kafka хранятся события старых версий (бессрочный retention, ADR-0002), и replay читает их новым кодом.

Поэтому:

- Правила версионирования из ADR-0002 (п. 5) обязательны и в монорепо.
- Несовместимое изменение — новый файл `*.v2.ts`. Старая версия не удаляется, пока события этой версии есть в топиках.
- Для каждой старой версии в `libs/contracts` есть **upcaster** — функция преобразования v1 → v2. Consumer работает только с последней версией, старые события приводятся к ней при чтении.
- **Контракт-тесты:** для каждой версии события в `libs/contracts` лежит JSON-фикстура. Тест проверяет, что фикстура проходит свою схему, а upcaster приводит её к последней версии. Удалить или незаметно сломать старую версию не получится.

### 6. Сборка и Docker

- **Nest-сервисы:** образ готовится через `nx prune <app>`. В выходной папке оказываются только production-зависимости сервиса и нужные ему workspace-пакеты. Multi-stage Dockerfile. Опция `generatePackageJson` в этой настройке не поддерживается.
- **Next.js:** `output: 'standalone'`; корень трассировки файлов — корень монорепо, иначе workspace-пакеты не попадут в сборку.
- Docker-образы собираются только для затронутых приложений.

### 7. CI

```yaml
- uses: actions/checkout@v4
  with:
    fetch-depth: 0 # нужна история для сравнения с базовым коммитом
- uses: pnpm/action-setup@v4
- uses: actions/setup-node@v4
  with:
    node-version: lts/*
    cache: pnpm
- uses: nrwl/nx-set-shas@v4 # определяет базовый коммит для affected
- run: pnpm install --frozen-lockfile
- run: pnpm nx affected -t lint typecheck test build
```

- `lint` включает проверку границ модулей.
- Изменение `libs/contracts` затрагивает все проекты — это ожидаемо.
- Достаточно локального кэша Nx. Удалённый кэш для одного разработчика не нужен.

## Последствия

**Плюсы**

- Контракт и все его потребители меняются одним коммитом, несовместимость ловит компилятор.
- CI прогоняет только затронутые проекты.
- Границы модулей проверяются автоматически, а не на code review.
- Новый сервис создаётся генератором за минуты.

**Минусы и цена**

- Зависимость от Nx и его соглашений. Обновления через `nx migrate` иногда требуют ручных правок.
- Порог входа: нужно разобраться в плагинах, inferred tasks, project references.
- Единые версии зависимостей: обновление NestJS затрагивает все сервисы сразу. Для одного разработчика это скорее плюс.
- Риск ложной уверенности, что монорепо решает совместимость контрактов. Закрыт п. 5.

## Связанные решения

- ADR-0001: микросервисная архитектура.
- ADR-0002: Kafka как брокер доменных событий.
- ADR-0004: Database per service (Prisma, генерация клиента как Nx-задача).
- ADR-0005: checkout saga (контракты команд).
- ADR-0006: `libs/auth`.
- ADR-0007: схема денег в `libs/contracts`.

## Когда пересмотреть решение

- Обновления Nx стабильно отнимают больше времени, чем экономят генераторы → Turborepo или pnpm workspaces.
- У сервиса появляется отдельная команда с независимым циклом релизов → вынести его в отдельный репозиторий, а контракты публиковать пакетом.
