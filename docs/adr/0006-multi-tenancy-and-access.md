# ADR-0006: Изоляция продавцов и доступ

**Статус:** Принято · **Дата:** 2026-10-23 · **Ревизия:** 3

## Контекст

Маркетплейс (ТЗ, раздел 1): в одних и тех же таблицах лежат товары, склады, остатки, под-заказы, клиенты и деньги многих продавцов. Продавец и его сотрудники должны видеть и менять только данные своего магазина. Покупатель — только свои заказы. Админ платформы — всё.

Утечка между продавцами — самый дорогой класс ошибок маркетплейса: чужие цены, остатки, покупатели и выручка. Типичная причина — один забытый фильтр по продавцу в одном запросе (IDOR, insecure direct object reference).

## Рассмотренные варианты

| Вариант                                                | Плюсы                                           | Минусы                                                                                                                               |
| ------------------------------------------------------ | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| База или схема Postgres на продавца                    | Полная изоляция                                 | Тысячи продавцов — тысячи баз или схем; миграции и запросы через всех продавцов (админка, saga, отчёты) становятся сложными          |
| **Общие таблицы + `seller_id`, проверка в приложении** | Просто и гибко; работает с Prisma без ухищрений | Одна забытая проверка — утечка. Нужны обязательный API доступа к данным и тесты                                                      |
| Общие таблицы + Row-Level Security в Postgres          | Проверку выполняет база — её нельзя забыть      | С Prisma каждый запрос должен идти в транзакции с `set_config`; обработчикам событий и админке нужен явный обход; сложнее отлаживать |

Выбрано: **общие таблицы с `seller_id` и обязательной областью доступа в каждом запросе** (п. 5) плюс автотесты изоляции (п. 8). RLS добавляется на этапе hardening как вторая линия защиты (п. 9).

## Решение

### 1. Модель

- **Арендатор — продавец** (магазин, `sellerId`). Профилем продавца и статусом его модерации владеет catalog (ADR-0001, п. 2).
- **Членство и права** сотрудников магазина хранит auth.
- В MVP пользователь состоит не более чем в одном магазине. Покупать он может при этом как обычный покупатель.
- Регистрация магазина: пользователь создаёт магазин в catalog → `seller.registered { sellerId, ownerUserId }` → auth делает его владельцем магазина. Права появятся в токене после ближайшего обновления.

### 2. Роли и права

| Роль                         | Область доступа                                                     |
| ---------------------------- | ------------------------------------------------------------------- |
| `buyer`                      | Свои корзина и заказы                                               |
| `seller` — владелец магазина | Все данные своего магазина, все права ниже, управление сотрудниками |
| `seller_manager`             | Данные своего магазина в пределах выданных прав                     |
| `admin`                      | Все данные платформы                                                |

Права сотрудника (выдаёт владелец):

| Право       | Что открывает                            |
| ----------- | ---------------------------------------- |
| `catalog`   | Товары, SKU, цены, отправка на модерацию |
| `warehouse` | Склады и остатки                         |
| `orders`    | Под-заказы: отгрузка, доставка, отмена   |
| `support`   | CRM: покупатели магазина                 |
| `finance`   | Баланс, операции, запрос выплаты         |

Управление сотрудниками (право `staff`) есть только у владельца и сотруднику не выдаётся.

Сотрудник добавляется без приглашения: владелец указывает email уже зарегистрированного пользователя и сразу выдаёт права. Пользователь состоит не больше чем в одном магазине: занятый — `409`. Приглашение письмом появится с notification (SD-05, решение 2).

Статус продавца:

- `pending` — кабинет доступен, товары можно готовить, но не публиковать;
- `active` — всё доступно;
- `rejected`, `blocked` — товары сняты с публикации (catalog публикует `product.*`), права кабинета отзываются при следующем обновлении токена.

### 3. Токен

```json
{
  "sub": "usr_01J9Z…",
  "roles": ["buyer", "seller_manager"],
  "sellerId": "slr_01J9Y…",
  "scopes": ["warehouse", "orders"],
  "exp": 1792653600
}
```

- Подпись асимметричная (EdDSA или RS256). Публичный ключ auth отдаёт по JWKS: `/.well-known/jwks.json`.
- Права и роли меняются при обновлении токена, то есть в течение 15 минут (ТЗ, 3.1). Мгновенный отзыв — после MVP.

### 4. Проверка токена

- gateway проверяет токен и отклоняет невалидные запросы.
- **Каждый сервис проверяет подпись сам** через `libs/auth` (guard + кэш ключей JWKS) и не доверяет заголовкам с идентичностью вроде `X-User-Id`. Если кто-то получит доступ во внутреннюю сеть, подделать пользователя без ключа он не сможет.
- Эндпоинт кабинета объявляет нужное право декоратором, например `@SellerScope('orders')`. Без нужного права — `403`.

### 5. Данные

- Каждая таблица с данными продавца содержит `seller_id NOT NULL`. Индексы начинаются с `seller_id`, уникальность — в пределах продавца, например `UNIQUE (seller_id, sku_code)`.
- **Исключение:** таблицы, где рядом с данными продавцов лежат данные платформы, например `ledger_entries` со счетами `cash:psp` и `commission:*` (ADR-0007). Там `seller_id` допускает `NULL`, а `NULL` означает «платформа». Запрос продавца всё равно фильтрует `seller_id = $scope.sellerId`, поэтому строки платформы ему не видны.
- **`skuCode` — артикул продавца**, уникален только в его магазине. Между сервисами, в командах, событиях и ключах партиций используется глобальный `skuId` (UUID v7, выдаёт catalog). Иначе одинаковые артикулы двух продавцов попадут в один резерв, ключ и расчёт.
- Идентификаторы — непоследовательные (UUID v7 или ULID с префиксом). Перебором `id + 1` чужие записи не найти.
- **Каждый метод репозитория принимает область доступа первым аргументом:**

  ```ts
  type AccessScope =
    | { kind: "buyer"; userId: string }
    | { kind: "seller"; sellerId: string; scopes: SellerPermission[] }
    | { kind: "platform" }; // админ и обработчики событий

  subOrders.findById(scope, subOrderId);
  // seller   → WHERE sub_order_id = $1 AND seller_id = $scope.sellerId
  // buyer    → WHERE sub_order_id = $1 AND buyer_id = $scope.userId
  // platform → WHERE sub_order_id = $1
  ```

- Область доступа строится только из проверенного токена (`libs/auth`). Область `platform` создаётся только в админских use cases (роль `admin`) и в обработчиках событий — никогда из запроса продавца или покупателя.
- **Чужой ресурс — `404`, а не `403`:** ответ не должен подтверждать, что такой объект существует.

### 6. Данные покупателя у продавца

- В под-заказе продавец видит то, что нужно для доставки: имя получателя, адрес, телефон.
- Email покупателя продавец не видит никогда.
- CRM продавца показывает только покупателей, у которых есть заказы в этом магазине, и только их заказы в этом магазине, без контактов.

### 7. События и админ

- События об агрегатах продавца несут `sellerId` в payload. Обработчик пишет данные с `sellerId` из события и работает в области `platform`.
- Действия админа пишутся в структурный лог: кто, что, над каким объектом. Отдельный журнал аудита — после MVP.

### 8. Тесты изоляции

- Для каждого эндпоинта кабинета — e2e-тест с двумя продавцами: продавец B получает `404` на ресурсы продавца A, а сотрудник без нужного права — `403`.
- Список эндпоинтов для таких тестов строится из метаданных декоратора `@SellerScope`. Новый эндпоинт кабинета автоматически попадает в проверку, забыть его нельзя.
- Те же проверки для покупателей: покупатель B не видит заказы покупателя A.

### 9. Row-Level Security (этап hardening)

Вторая линия защиты на случай ошибки в коде:

```sql
ALTER TABLE stock ENABLE ROW LEVEL SECURITY;
ALTER TABLE stock FORCE ROW LEVEL SECURITY;   -- действует и на владельца таблицы (ADR-0004)

CREATE POLICY seller_isolation ON stock
  USING (
    current_setting('app.bypass_tenant', true) = 'on'
    OR seller_id = current_setting('app.seller_id', true)
  );

-- в каждой транзакции запроса продавца:
SELECT set_config('app.seller_id', $1, true);   -- true: только до конца транзакции
```

Для этого все запросы кабинета пойдут в транзакциях, а обработчики событий и админка — с `app.bypass_tenant = on`. Решение о включении — по итогам этапов 3–8.

## Последствия

**Плюсы**

- Изоляция обеспечивается API доступа к данным и проверяется автоматически, а не держится на внимательности.
- Одна схема данных на всех продавцов: простые миграции и запросы платформы.

**Минусы и цена**

- Обязательная область доступа в каждом методе репозитория — больше параметров и шаблонного кода.
- До включения RLS одна ошибка в репозитории остаётся возможной; её должны ловить тесты из п. 8.
- Права обновляются с задержкой до 15 минут.

**Правила для code review**

- метод репозитория без области доступа;
- область `platform` в коде, который обрабатывает запрос продавца или покупателя;
- таблица с данными продавца без `seller_id NOT NULL`;
- эндпоинт кабинета без `@SellerScope`;
- `403` на чужой ресурс вместо `404`;
- доверие заголовкам с идентичностью вместо проверки токена.

## Когда пересмотреть решение

- Пользователь должен работать в нескольких магазинах → в токен добавляется выбор активного магазина.
- Нужен мгновенный отзыв прав → список отозванных токенов или короткий срок жизни access-токена.
