# ADR-0001: Микросервисная архитектура с поэтапным запуском

**Статус:** Принято · **Дата:** 2026-10-22 · **Ревизия:** 7

## Контекст

Pet-проект для практики System Design: multi-vendor маркетплейс с ERP и CRM (ТЗ). Домены естественно разделяются на bounded contexts, между ними много асинхронных взаимодействий. Разработчик один.

### Драйверы решения (по приоритету)

1. **Учебная ценность.** Главный драйвер. Нужно столкнуться с реальными проблемами распределённых систем: сетевыми сбоями, отдельными БД, eventual consistency, saga, replay.
2. **Управляемая сложность.** Проект не должен утонуть в инфраструктуре. Каждый этап заканчивается работающим сквозным сценарием.
3. **Локальный запуск** на одном ноутбуке одной командой.

## Рассмотренные варианты

| Вариант                           | Плюсы                                                                                                 | Минусы                                                                                   | Оценка для этого проекта                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Модульный монолит                 | Одна транзакция, один деплой, простая отладка. Outbox, Kafka и идемпотентность отрабатываются и здесь | Нет сетевых сбоев между модулями, отдельных БД, независимого деплоя, распределённой saga | Правильный выбор для реального продукта с одним разработчиком |
| Монолит, потом выделение сервисов | Быстрый старт; границы проверяются на практике до выделения                                           | Распределённые паттерны появляются поздно                                                | Хорош, если цель — продукт, а не практика                     |
| **Микросервисы поэтапно**         | Реальные распределённые проблемы с первого этапа                                                      | Много обвязки, сложнее отладка и локальный запуск                                        | **Выбран:** соответствует главному драйверу                   |

В реальном проекте с одним разработчиком мы выбрали бы модульный монолит. Здесь микросервисы выбраны сознательно, ради практики. Риск «утонуть в обвязке» снижается поэтапным запуском и шаблоном сервиса.

## Решение

### 1. Сервисы

8 backend-сервисов и 2 фронтенд-приложения в Nx-монорепозитории (ADR-0003).

Backend (NestJS):

| Сервис       | Ответственность                                                                                                                                     |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| gateway      | Единственная точка входа: маршрутизация, проверка JWT, rate limit, `X-Request-Id`                                                                   |
| auth         | Учётные записи, аутентификация, выпуск JWT, членство в магазинах и права сотрудников                                                                |
| catalog      | Продавцы и их модерация, категории, товары и SKU, цены, модерация товаров, поиск                                                                    |
| order        | Корзина, заказы и под-заказы, оркестрация saga оформления, статусы под-заказов                                                                      |
| payment      | Деньги: авторизация, списание, возвраты, журнал проводок, комиссия, удержание, выплаты (ADR-0007). Внешний провайдер локально — заглушка `fake-psp` |
| erp          | Склады продавцов, остатки, резервы, списание при отгрузке, реестр продаж                                                                            |
| crm          | Клиенты 360°, метрики, сегменты; CRM продавца                                                                                                       |
| notification | Уведомления покупателям и продавцам                                                                                                                 |

Frontend (Next.js):

| Приложение | Назначение                                                        |
| ---------- | ----------------------------------------------------------------- |
| storefront | Витрина: каталог, поиск, корзина, оформление и оплата, мои заказы |
| backoffice | Кабинет продавца и админка платформы                              |

Наружу открыт только gateway. Остальные сервисы доступны только во внутренней docker-сети. Фронты и webhook платёжного провайдера обращаются только к gateway и никогда напрямую к сервисам.

### 2. Владение данными

**У каждой сущности ровно один владелец.** Только владелец пишет эти данные и публикует события об их изменении. Остальные сервисы держат у себя локальные копии нужных им полей (read-модели), построенные по событиям, и никогда не читают чужую БД. Технические правила изоляции и read-models — ADR-0004.

| Данные                                                         | Владелец     | Как получают остальные                                 |
| -------------------------------------------------------------- | ------------ | ------------------------------------------------------ |
| Учётная запись, email, роли, членство в магазине и права       | auth         | JWT-claims; события `user.*`                           |
| Продавец (магазин), статус модерации                           | catalog      | События `seller.*`                                     |
| Категории, товары, SKU, цены продажи                           | catalog      | События `product.*` → read-модель в order              |
| Склады, остатки, резервы                                       | erp          | События `stock.*`; резерв — шаг saga                   |
| Реестр продаж                                                  | erp          | API erp                                                |
| Корзина, заказы, под-заказы и их статусы                       | order        | События `order.*`, `sub-order.*`                       |
| Платежи, проводки, балансы продавцов, ставки комиссии, выплаты | payment      | События `payment.*`, `payout.*`; балансы — API payment |
| Профили клиентов, метрики, сегменты                            | crm          | API crm                                                |
| Отправленные уведомления                                       | notification | —                                                      |

Правила:

- Цена фиксируется в строке заказа в момент оформления (snapshot). Последующее изменение цены в catalog на заказ не влияет.
- Профиль клиента в crm создаётся по событию `user.registered` и связан с учётной записью через `userId`.
- notification берёт контактные данные из payload события или из своей read-модели по `user.*`.
- Данные продавца изолированы от других продавцов — ADR-0006.
- Деньги меняются только в payment — ADR-0007.

### 3. Взаимодействие сервисов

| Тип                               | Механизм                       | Когда                                      |
| --------------------------------- | ------------------------------ | ------------------------------------------ |
| Интеграции между доменами         | События Kafka (ADR-0002)       | По умолчанию                               |
| Шаги saga                         | Команды через Kafka (ADR-0005) | Только оркестратор — order                 |
| Внешние запросы                   | REST через gateway             | Клиент → система                           |
| Синхронное чтение между сервисами | REST                           | Только чтение, когда read-модель неуместна |

Правила синхронных вызовов:

- Только чтение. Изменение чужих данных — только через события или saga.
- Таймаут обязателен (стартовое значение 2 с). Ретраи — только для идемпотентных GET.
- Глубина цепочки — не больше одного перехода: A → B допустимо, A → B → C — нет.
- Сервис должен работать (пусть и с деградацией), если синхронная зависимость недоступна.

Saga оформления заказа — ADR-0005: оркестрация в order-сервисе, резерв до оплаты, оплата в два шага (авторизация и списание), команды через Kafka (`<context>.commands`).

### 4. Базы данных

Database per service: у каждого сервиса своя база в общем контейнере Postgres и свой пользователь с доступом только к ней. Миграции выполняются отдельным шагом перед стартом сервиса. Один контейнер Postgres — допустимая точка отказа для локального окружения.

Подробности (пользователи и права, read-models, Prisma, бюджет соединений, миграции, бэкапы) — ADR-0004.

### 5. Общие библиотеки (`libs/`)

**Разрешено** — только техническое:

| Библиотека           | Содержание                                                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `libs/kafka`         | Адаптер Kafka, конверт сообщения, DLQ (ADR-0002)                                                                         |
| `libs/outbox`        | Таблица и relay для outbox                                                                                               |
| `libs/idempotency`   | `processed_events`, обёртка обработчика                                                                                  |
| `libs/observability` | Логгер, OpenTelemetry, проброс `correlationId` и trace-контекста                                                         |
| `libs/auth`          | Проверка JWT по JWKS, область доступа, декоратор прав (ADR-0006)                                                         |
| `libs/contracts`     | Схемы событий, команд и публичных API с версиями, схема денег: TS-типы + zod, без зависимостей от фреймворков (ADR-0003) |

**Запрещено:** доменные сущности, бизнес-логика, общие репозитории БД. Если два сервиса хотят общий доменный код, это сигнал пересмотреть границу между ними.

### 6. Наблюдаемость

- **Трейсинг:** OpenTelemetry SDK в каждом сервисе, Jaeger в docker-compose. Trace-контекст (W3C `traceparent`) передаётся в HTTP-заголовках и в заголовках Kafka-сообщений через `libs/kafka`. Одна операция пользователя видна в Jaeger как один трейс через все сервисы.
- **Логи:** структурированный JSON (pino), в каждой записи `traceId`, `correlationId`, `service`.
- **Correlation-id:** gateway берёт `X-Request-Id` из запроса или генерирует его; дальше он идёт в HTTP-заголовках и в поле `correlationId` конверта сообщения (ADR-0002).
- **Health-check:** у каждого сервиса `/health/live` и `/health/ready` (БД и Kafka доступны).

### 7. Локальный запуск

docker compose с профилями, чтобы не поднимать всё сразу:

| Профиль | Состав                                      |
| ------- | ------------------------------------------- |
| `infra` | Postgres, Kafka, Kafbat UI, Jaeger, Mailpit |
| `core`  | `infra` + gateway, order, payment, fake-psp |
| `full`  | Все сервисы и фронтенды                     |

Пример: `docker compose --profile core up`.

### 8. Шаблон сервиса

Новый сервис создаётся из шаблона, а не копипастой. В шаблоне уже есть: Prisma-клиент и подключение к своей БД, шаг миграций в compose (ADR-0004), outbox и relay, обёртка идемпотентного обработчика, проверка JWT и область доступа (ADR-0006), OpenTelemetry и логгер, health-check, Dockerfile, сервис в docker-compose. Цель — новый сервис поднимается за минуты, и время уходит на домен, а не на обвязку.

## Этапы

План этапов и их критерии готовности — ТЗ, раздел 8. Принципы, по которым он построен:

- **Сквозной сценарий раньше полноты сервисов.** Первым делается оформление заказа через несколько сервисов, а не CRUD каждого сервиса по очереди. Иначе месяцы уходят на обвязку, а распределённые проблемы появляются в самом конце.
- **Упрощения ранних этапов снимаются позже:** до этапа с auth — JWT-заглушка в gateway с тестовыми покупателями и продавцами; до этапа с catalog — seed-товары в read-модели order.
- **Libs выносятся по факту:** доменный и прикладной код попадает в библиотеку, когда уже понадобился в двух сервисах. Исключение — технические libs шины и БД (`contracts`, `kafka`, `outbox`, `idempotency`, `observability`): они нужны каждому сервису по ADR-0002 и ADR-0004 и делаются на этапе 1 вместе с шаблоном сервиса (п. 8), а их первый потребитель — `demo`-сервис генератора (SD-01).
- **Фронты не входят в критерии ранних этапов:** сценарии проверяются HTTP-запросами к gateway (e2e-тесты, `.http`-файлы). Storefront и backoffice развиваются параллельно, по мере того как gateway отдаёт нужные сценарии.

## Последствия

**Плюсы**

- Реальная практика распределённых паттернов: outbox, идемпотентность, saga, replay, трейсинг.
- Изоляция доменов: у каждого сервиса своя БД и свои миграции.
- Каждый этап даёт работающий сценарий, который можно показать.

**Минусы и цена**

- Eventual consistency: данные между сервисами синхронизируются с задержкой.
- Дублирование данных в read-моделях.
- Сложнее отладка; частично компенсируется трейсингом.
- Заметная нагрузка на ноутбук при профиле `full`.

**Риски и защита**

| Риск                                                                 | Защита                                                                         |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Обвязка съедает время, до доменной логики дело не доходит            | Этапы со сквозными сценариями, шаблон сервиса                                  |
| Распределённый монолит: сервисы связаны через общий код или чужие БД | Владение данными (п. 2), правила libs (п. 5), отдельные пользователи БД (п. 4) |
| Утечка данных между продавцами                                       | Область доступа в каждом запросе и тесты изоляции (ADR-0006)                   |
| Ошибки в деньгах                                                     | Журнал проводок с инвариантами в одном сервисе (ADR-0007)                      |
| Цепочки синхронных вызовов и каскадные отказы                        | Правила синхронных вызовов (п. 3)                                              |
| Невозможно понять, где сломался процесс                              | Трейсинг и correlation-id (п. 6)                                               |

## Связанные решения

- ТЗ: требования и план этапов.
- ADR-0002: Kafka как брокер доменных событий.
- ADR-0003: Nx monorepo.
- ADR-0004: Database per service.
- ADR-0005: checkout saga.
- ADR-0006: изоляция продавцов и доступ.
- ADR-0007: деньги — журнал проводок, комиссия, удержание, выплаты.
- SD-00: обзор архитектуры — схемы C4 и каталог сообщений.

## Открытые вопросы

- Нужен ли gRPC для внутренних синхронных вызовов или достаточно REST.

## Когда пересмотреть решение

- Два сервиса всегда меняются вместе → объединить их.
- Обвязка стабильно занимает больше времени, чем доменная логика → сократить число сервисов поздних этапов (например, оставить notification модулем crm).
- Проект превращается в продукт с реальными пользователями → пересмотреть в пользу модульного монолита для части доменов.
