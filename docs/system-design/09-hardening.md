# System Design 09: Hardening (этап 9)

**Статус:** ✅ Реализовано · **Дата:** 2026-10-29 · **Ревизия:** 3

Этап 9 из ТЗ (раздел 8): целевые показатели нагрузки достигнуты, Grafana, RLS как вторая линия изоляции продавцов. Функциональность MVP готова на этапах 1–8; этот этап её не расширяет, а измеряет и укрепляет. ТЗ, раздел 5: целевые показатели фиксируются до начала этапа — их фиксирует согласование этого документа (п. 2, решение 1). Правила заданы в ADR-0001 (наблюдаемость), ADR-0002 (outbox, lag потребителей), ADR-0004 (база на сервис, роли), ADR-0006, п. 9 (RLS).

## 2. Целевые показатели (согласовано)

Стенд — compose-профиль `full` на CI-раннере GitHub `ubuntu-latest` публичного репозитория (4 vCPU, 16 ГБ), вместе с генератором нагрузки: у разработчика нет Docker, а цифры должны воспроизводиться одной кнопкой (решение 1, ревизия 3). Это пет-проект на одной машине: цель — показать, что архитектура держит разумный поток без потерь, а не масштаб продакшена. Нагрузка ровная, 5 минут после 1 минуты разгона.

| Поток                                         | Цель                             | p95 ответа         | Ошибки  |
| --------------------------------------------- | -------------------------------- | ------------------ | ------- |
| Каталог: поиск и карточка (гости)            | 50 RPS                           | < 300 мс           | < 1 %   |
| Оформление: `POST /orders` (вошедшие)         | 5 заказов/с                      | < 500 мс до `202`  | < 1 %   |
| Оформление: оплата → `CONFIRMED`              | тот же поток                     | < 5 с              | 0 зависших |
| Кабинет: заказы, остатки, баланс              | 10 RPS                           | < 500 мс           | < 1 %   |
| Lag потребителей и задержка outbox            | —                                | < 10 с под нагрузкой, 0 через минуту после | — |

Цифры зафиксированы согласованием SD-09 (ТЗ, раздел 5).

## 3. Нагрузочные тесты

- **k6** (`grafana/k6` в compose-профиле `tools`), сценарии в `apps/load` (`*.k6.js`): каталог, оформление с оплатой через тестовое API fake-psp, кабинет. Пороги k6 (`thresholds`) — значения п. 2: превышение — тест красный.
- Данные: демо-витрина и тестовые пользователи (SD-07, решение 12); покупатели для оформления регистрируются в начале сценария. Остатки демо-SKU пополняются перед прогоном.
- Запуск — `apps/load/run.sh`: стенд `full` с настройками `compose.load.yaml` (лимит gateway поднят, трейсы — каждый десятый корневой запрос), сценарии с минутой разгона, затем проверки п. 1, сценарии 4–5, и диагностика: CPU контейнеров, p95 по сервисам и обработчикам, lag по группам. В CI — отдельный workflow `load` по кнопке (`workflow_dispatch`) и раз в неделю: 10 минут нагрузки не нужны на каждый push. Отчёт k6 и загрузка контейнеров — артефактом `load-report`.
- Подбор ёмкости — вход `sweep` workflow (`LOAD_SWEEP="0.5 1 2 3"`): k6 на каждом потоке заказов по 2 минуты при тех же каталоге и кабинете, таблица p95 — в журнале job. Пороги и проверки — только в обычном прогоне.

## 4. Метрики и Grafana

- Метрики — **OpenTelemetry** в `libs/observability`: те же HTTP- и undici-инструментации, что для трейсов, дают гистограммы длительности запросов. Свои метрики: обработка сообщения (тип, исход), задержка outbox (возраст самой старой неопубликованной записи), lag потребителя по партициям, переходы saga оформления.
- Экспорт — OTLP в **OpenTelemetry Collector**, из него трейсы — в Jaeger, метрики — в **Prometheus** (`remote write`). Сервисы не открывают новых портов; сбор в одном месте.
- **Grafana** (порт 3005, профиль `infra`): источники — Prometheus и Jaeger, дашборды и источники — provisioning из репозитория (`infra/grafana`). Логи остаются в stdout (pino) — Loki после MVP.

## 5. RLS — вторая линия изоляции

По ADR-0006, п. 9. Первая линия — обязательная область доступа в каждом методе репозитория и автотесты изоляции — остаётся; RLS ловит ошибку, которая прошла мимо них.

| Сервис  | Таблицы с политикой `seller_isolation`                       |
| ------- | ------------------------------------------------------------ |
| catalog | `products`, `skus`                                           |
| erp     | `warehouses`, `stock`, `stock_thresholds`, `reservations`, `sales` |
| order   | `sub_orders`, `order_lines`                                  |
| payment | `ledger_entries`, `settlements`, `payouts`                   |
| crm     | `customer_orders`, `timeline`                                |

- `ENABLE` и `FORCE ROW LEVEL SECURITY` — миграцией каждого сервиса (`FORCE`: роль сервиса — владелец таблиц, ADR-0004); политика пропускает строку, если `app.bypass_tenant = 'on'` или `app.seller_id` совпадает с её `seller_id`. Сравнение — текстом: пустая настройка не ломает запрос приведением к `uuid`.
- Роль сервиса работает с `app.bypass_tenant = on` по умолчанию (`ALTER ROLE <svc>_svc SET …` в provisioning): обработчики событий, saga, админка, витрина, seed и скрипты не меняются и не платят лишний круг к базе (решение 5, ревизия 2).
- Каждый эндпоинт кабинета (`@SellerScope`) работает в режиме магазина: перехватчик кладёт `sellerId` в контекст запроса, и каждый запрос Prisma в нём идёт в транзакции, первой командой `set_config('app.bypass_tenant', 'off', true)` и `set_config('app.seller_id', $1, true)` (до конца транзакции, пул соединений не загрязняется). Так RLS защищает и запрос, в котором забыли условие по магазину; новый эндпоинт кабинета защищён сразу.
- Read-модели чужих сервисов (`catalog_skus` в order и erp и т. п.) — данные платформы, без RLS. auth (`memberships`) — без RLS: сотрудников меняет только владелец через auth, а вход читает членство без области.

## 6. Решения (согласовано)

1. **Целевые показатели — п. 2**, стенд — CI-раннер `ubuntu-latest` публичного репозитория (4 vCPU, 16 ГБ), нагрузка 5 минут (ревизия 3). Цифры не снижены — сменился стенд: у приватного репозитория кончились минуты Actions, а у публичного они бесплатны и раннер вдвое больше. _Было (ревизии 1–2):_ раннер приватного репозитория, 2 vCPU и 7 ГБ. На нём сервисы, Kafka, Postgres и k6 делили два ядра, и оформление 5 заказов/с не укладывалось: обработчики saga в order — p95 1,5–1,9 с, lag order-service до 25 сообщений, от оплаты до `CONFIRMED` — p95 57 с, 28 заказов без итога за минуту ожидания. Запасной вариант — цели по фактической ёмкости, подобранной `sweep`. _Альтернатива:_ свой сервер с Docker — тогда цифры можно поднять.
2. **k6**, а не Gatling или Locust: сценарии на JavaScript рядом с кодом, пороги — частью теста, образ без JVM.
3. **Нагрузочный прогон — отдельный workflow по кнопке и раз в неделю**, а не в каждом push: 10 минут и весь стенд.
4. **Метрики — OpenTelemetry → Collector → Prometheus**, а не `prom-client` и scrape каждого сервиса: инструментации уже есть, портов не добавляется.
5. **RLS: `app.bypass_tenant = on` по умолчанию на роль сервиса, кабинет — в режиме магазина** (ревизия 2). Политика — как в ADR-0006, п. 9, но платформа работает с флагом по умолчанию, а не включает его в каждой транзакции: каждый запрос кабинета защищён, а платформенный код не меняется и не платит лишний круг к базе на этапе замеров нагрузки. _Было (ревизия 1):_ отказ по умолчанию для всех соединений — забытый путь закрыт полностью, но правки во всех пяти сервисах и `set_config` в каждой транзакции платформы. Код вне кабинета не работает от имени продавца, и RLS его не ограничивает.
6. **Grafana — в профиле `infra`** рядом с Jaeger: её смотрят и при обычной разработке.

## 7. Порядок работ

1. OpenTelemetry Collector, Prometheus, Grafana в compose; метрики в `libs/observability`; дашборды; проверка в CI `infra-smoke`.
2. RLS: обёртки транзакций, миграции сервисов; интеграционные тесты «без условия по магазину — только свои строки», «без области — ошибка»; e2e этапов 2–8 с RLS.
3. k6: сценарии, `apps/load/run.sh`, `compose.load.yaml`, workflow `load`.
4. Прогон, разбор узких мест, исправления; прогон до зелёных порогов.
5. CHANGELOG, SD-09 → «Реализовано», ТЗ: этап 9 ✅, SD-00, README.

## 8. Итог

Прогон 2026-10-29 (коммит `5325687`) на `ubuntu-latest` публичного репозитория (4 vCPU, 16 ГБ, Ubuntu 26.04), стенд и k6 на одной машине, 1 минута разгона и 5 минут ровной нагрузки:

| Поток                                  | Цель                                       | Факт                                                                 |
| -------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------- |
| Каталог: поиск и карточка, 50 RPS      | p95 < 300 мс, ошибки < 1 %                 | p95 35 мс, 0 ошибок из 16 499 запросов                               |

| Деньги после нагрузки                  | журнал без проблем, расчёты = реестр продаж | сверка журнала `ok`; у магазинов A и B расчёты payment равны реестру erp (832 и 817 под-заказов) |

Время до `CONFIRMED` k6 меряет опросом раз в секунду, как витрина: точность — секунда, и минимум — 1,01 с. Загрузка CPU за прогон (100 % — одно ядро): Kafka 48 %, Postgres 41 %, order 38 %, gateway 32 %, payment и catalog по 23 %, остальные ниже 16 %. Обработчики сообщений — p95 0,03–0,16 с (дольше всех `payment.capture-payment`), повторов нет.

Уточнения по ходу реализации:

- **Collector 0.162** переименовал компоненты в snake_case: `otlp_http`, `prometheus_remote_write`, `kafka_metrics`; старые имена — устаревшие алиасы. Образ distroless: готовность проверяется по `health_check` с соседнего контейнера.
- **Lag групп** в Prometheus — `kafka_consumer_group_lag_ratio`: у метрики единица «1», и перевод OTLP → Prometheus добавляет суффикс. Проверки и дашборд принимают имя с суффиксом и без.
- **Возраст очереди outbox**: накопительный gauge SDK держит последнее значение и без новых наблюдений, поэтому не-лидер relay сообщает 0, а дашборд берёт максимум по сервису. Гистограммы в секундах — со своими границами: у SDK по умолчанию миллисекундные.
- **Jaeger из Grafana** — источник данных и ссылка «Трейсы (Jaeger)» на дашборде; переход к трейсу из точки графика (exemplars) — после MVP.
- **RLS включается в драйвер-адаптере Prisma**, а не в API клиента: так под режим магазина попадают и raw SQL, и интерактивные транзакции. Запросы Prisma ленивые — уходят в базу на `then`, поэтому `runAsTenant` сам запускает результат-thenable. Суперпользователь Testcontainers обходит RLS — тест работает ролью без привилегий.
- **Нагрузка**: `Idempotency-Key` — только UUID; k6 опрашивает статус заказа раз в секунду, как витрина; на стенде нагрузки трейсы — каждый десятый корневой запрос.
- **Узкое место оформления — order**: обработчики saga шли по 3 партиции из 12, около 3 сообщений в секунду при нужных 25. Параллельно обрабатывается 6 партиций — по числу партиций топиков сервиса; внутри партиции порядок строгий (ADR-0002, п. 7). У order пул из 10 соединений с базой: горячий путь оформления, шесть обработчиков saga и HTTP делят один пул (ADR-0004, ревизия 6).
- **Стенд — 4 vCPU** (ревизия 3, решение 1): на 2 vCPU после этих правок оформление всё равно упиралось в CPU. Подбор ёмкости `sweep` остался в workflow — для проверки запаса после изменений.
- **Диск раннера**: образы сервисов и миграций с `node_modules` не помещались — job `e2e` и workflow `load` перед сборкой удаляют ненужные SDK и образы Docker.
