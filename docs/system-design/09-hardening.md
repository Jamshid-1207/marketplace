# System Design 09: Hardening (этап 9)

**Статус:** На согласовании · **Дата:** 2026-10-25 · **Ревизия:** 1

Этап 9 из ТЗ (раздел 8): целевые показатели нагрузки достигнуты, Grafana, RLS как вторая линия изоляции продавцов. Функциональность MVP готова на этапах 1–8; этот этап её не расширяет, а измеряет и укрепляет. ТЗ, раздел 5: целевые показатели фиксируются до начала этапа — их фиксирует согласование этого документа (п. 2, решение 1). Правила заданы в ADR-0001 (наблюдаемость), ADR-0002 (outbox, lag потребителей), ADR-0004 (база на сервис, роли), ADR-0006, п. 9 (RLS).

## 2. Целевые показатели — на согласование

Стенд — compose-профиль `full` на CI-раннере GitHub `ubuntu-latest` приватного репозитория (2 vCPU, 7 ГБ), вместе с генератором нагрузки: у разработчика нет Docker, а цифры должны воспроизводиться одной кнопкой. Это пет-проект на одной машине: цель — показать, что архитектура держит разумный поток без потерь, а не масштаб продакшена. Нагрузка ровная, 5 минут после 1 минуты разгона.

| Поток                                         | Предлагается                     | p95 ответа         | Ошибки  |
| --------------------------------------------- | -------------------------------- | ------------------ | ------- |
| Каталог: поиск и карточка (гости)            | 50 RPS                           | < 300 мс           | < 1 %   |
| Оформление: `POST /orders` (вошедшие)         | 5 заказов/с                      | < 500 мс до `202`  | < 1 %   |
| Оформление: оплата → `CONFIRMED`              | тот же поток                     | < 5 с              | 0 зависших |
| Кабинет: заказы, остатки, баланс              | 10 RPS                           | < 500 мс           | < 1 %   |
| Lag потребителей и задержка outbox            | —                                | < 10 с под нагрузкой, 0 через минуту после | — |

Цифры — предложение; согласование фиксирует их или заменяет вашими.

## 3. Нагрузочные тесты

- **k6** (`grafana/k6` в compose-профиле `tools`), сценарии в `apps/load` (`*.k6.js`): каталог, оформление с оплатой через тестовое API fake-psp, кабинет. Пороги k6 (`thresholds`) — значения п. 2: превышение — тест красный.
- Данные: демо-витрина и тестовые пользователи (SD-07, решение 12); покупатели для оформления регистрируются в начале сценария. Остатки демо-SKU пополняются перед прогоном.
- Запуск — `apps/load/run.sh`: стенд `full` с настройками `compose.load.yaml` (лимит gateway поднят), прогрев, сценарии, затем проверки п. 1, сценарии 4–5. В CI — отдельный workflow `load` по кнопке (`workflow_dispatch`) и раз в неделю: 10 минут нагрузки не нужны на каждый push. Отчёт k6 и снимки дашбордов — артефактами.

## 4. Метрики и Grafana

- Метрики — **OpenTelemetry** в `libs/observability`: те же HTTP- и undici-инструментации, что для трейсов, дают гистограммы длительности запросов. Свои метрики: обработка сообщения (тип, исход), задержка outbox (возраст самой старой неопубликованной записи), lag потребителя по партициям, переходы saga оформления.
- Экспорт — OTLP в **OpenTelemetry Collector**, из него трейсы — в Jaeger, метрики — в **Prometheus** (`remote write`). Сервисы не открывают новых портов; сбор в одном месте.
- **Grafana** (порт 3005, профиль `infra`): источники — Prometheus и Jaeger, дашборды и источники — provisioning из репозитория (`infra/grafana`). Логи остаются в stdout (pino) — Loki после MVP.

## 5. RLS — вторая линия изоляции

По ADR-0006, п. 9. Первая линия — обязательная область доступа в каждом методе репозитория и автотесты изоляции — остаётся; RLS ловит ошибку, которая прошла мимо них.

| Сервис  | Таблицы с политикой `seller_isolation`                       |
| ------- | ------------------------------------------------------------ |
| catalog | `products`, `skus`                                           |
| erp     | `warehouses`, `stock`, `stock_thresholds`, `reservations`, `sales` |
| order   | `sub_orders`, `order_lines`                                  |
| payment | `ledger_entries`, `settlements`, `payouts`                   |
| crm     | `customer_orders`, `timeline`                                |

- `ENABLE` и `FORCE ROW LEVEL SECURITY` — миграцией каждого сервиса; политика пропускает строку, если `app.seller_id` совпадает с её `seller_id` или `app.bypass_tenant = 'on'`. Без настроек — ни одной строки: забытый путь закрывается, а не открывается.
- Запросы кабинета — в транзакции, первой командой `set_config('app.seller_id', $1, true)` (до конца транзакции, пул соединений не загрязняется). Обработчики событий, saga, админка и отчёты — `app.bypass_tenant = on` в своей транзакции. Обёртки — в `libs/idempotency` рядом с транзакциями обработчиков и новой `withTenant` для репозиториев кабинета.
- Read-модели чужих сервисов (`catalog_skus` в order и erp и т. п.) — данные платформы, без RLS. auth (`memberships`) — без RLS: сотрудников меняет только владелец через auth, а вход читает членство без области.

## 6. Решения — на согласование

1. **Целевые показатели — п. 2**, стенд — CI-раннер `ubuntu-latest` (2 vCPU, 7 ГБ), нагрузка 5 минут. _Альтернатива:_ ваши цифры или другой стенд — например, свой сервер с Docker, тогда цифры можно поднять.
2. **k6**, а не Gatling или Locust: сценарии на JavaScript рядом с кодом, пороги — частью теста, образ без JVM.
3. **Нагрузочный прогон — отдельный workflow по кнопке и раз в неделю**, а не в каждом push: 10 минут и весь стенд.
4. **Метрики — OpenTelemetry → Collector → Prometheus**, а не `prom-client` и scrape каждого сервиса: инструментации уже есть, портов не добавляется.
5. **RLS с отказом по умолчанию** (`app.bypass_tenant` для платформы), как в ADR-0006. _Альтернатива:_ политика пропускает всё, пока `app.seller_id` не задан, — меньше правок в обработчиках, но забытый путь остаётся открытым.
6. **Grafana — в профиле `infra`** рядом с Jaeger: её смотрят и при обычной разработке.

## 7. Порядок работ

1. OpenTelemetry Collector, Prometheus, Grafana в compose; метрики в `libs/observability`; дашборды; проверка в CI `infra-smoke`.
2. RLS: обёртки транзакций, миграции сервисов; интеграционные тесты «без условия по магазину — только свои строки», «без области — ошибка»; e2e этапов 2–8 с RLS.
3. k6: сценарии, `apps/load/run.sh`, `compose.load.yaml`, workflow `load`.
4. Прогон, разбор узких мест, исправления; прогон до зелёных порогов.
5. CHANGELOG, SD-09 → «Реализовано», ТЗ: этап 9 ✅, SD-00, README.
