# System Design 04: Деньги (этап 4)

**Статус:** ✅ Утверждено · **Дата:** 2026-10-23 · **Ревизия:** 1

Этап 4 из ТЗ (раздел 8): журнал проводок, комиссия, удержание и выплаты в payment. Правила уже заданы в ADR-0007 (счета, операции, инварианты), ADR-0005 (источники проводок) и ADR-0006 (право `finance`). Здесь — что именно строим на текущем коде и как проверяем.

## 1. Критерий готовности

ТЗ, раздел 8: «Сумма каждой проводки = 0. Баланс продавца сходится с реестром продаж erp. Отмена под-заказа даёт частичный возврат. Два одновременных запроса выплаты не выплачивают дважды». Сценарии этапов 2 и 3 остаются.

| #   | Сценарий                                                 | Ожидаемый результат                                                                                                    |
| --- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 1   | Заказ у двух продавцов оплачен                           | У каждого продавца «в ожидании» `S − C`; комиссия — по ставке самой глубокой категории позиции, иначе по умолчанию     |
| 2   | Под-заказ доставлен, срок удержания прошёл               | Сумма переходит в «доступно», комиссия — в заработанную                                                                |
| 3   | Под-заказ отменён до отгрузки                            | Частичный возврат `S` покупателю; «в ожидании» продавца уменьшилось на `S − C`; второй под-заказ не затронут            |
| 4   | Два одновременных запроса выплаты на весь доступный баланс | Проходит один, второй — `409`; у провайдера одна выплата                                                              |
| 5   | Выплата не прошла у провайдера                           | Сумма вернулась в «доступно»                                                                                           |
| 6   | Сверка с erp                                             | Сумма `S` расчётов продавца = продажи в реестре erp за вычетом сторно                                                   |
| 7   | Инварианты журнала после всех сценариев                  | Сумма каждой проводки = 0; балансы = суммам записей; «в ожидании» = расчётам `PENDING` и `HOLD`; доступное ≥ 0         |
| 8   | Админ меняет ставку категории                            | Новые заказы считаются по новой ставке, уже списанные — нет                                                            |
| 9   | Изоляция финансов                                        | Продавец B не видит финансы A; сотрудник без права `finance` — `403`; не-админ в API ставок — `403`                     |

Плюс интеграционные тесты ADR-0007, п. 9: повторный `CapturePayment` не создаёт вторую проводку; `UPDATE` записи журнала и несбалансированная проводка отклоняются базой. И property-based тест инвариантов.

## 2. Что входит и что нет

**Входит:**

- payment: журнал проводок с проверками в базе, балансы, расчёты по под-заказам, комиссия, удержание, выплаты, ежедневная сверка, API финансов продавца и админа.
- fake-psp: выплаты (`POST /v1/payouts`) с webhook результата и тестовым режимом отказа.
- Контракты: `payout.paid`, `payout.failed`.
- `libs/auth`: `@AdminScope()` — область `platform` только для роли `admin` (ADR-0006, п. 5).
- erp: сводка реестра продаж продавца для сверки.
- gateway: маршруты `/api/seller/finance/**`, `/api/seller/payouts/**`, `/api/admin/**`.

**Не входит:**

- Категории в catalog и события `category.*` — этап 5. До него read-model категорий в payment наполняется seed из `libs/contracts/src/dev` (решение 3).
- Автоматические выплаты, сверка с отчётами провайдера, закрывающие документы, возвраты после доставки — после MVP (ТЗ, 3.5; ADR-0007).
- UI кабинета и админки — этап 7.

## 3. Журнал

Таблицы, триггеры и инварианты — ADR-0007, п. 7, с типом `uuid` для id (SD-01, п. 6.1). Код:

- `domain/ledger.ts` — чистые функции: операция → записи проводки (`capturePosting`, `holdReleasePosting`, `refundRequestedPosting`, …). Каждая возвращает записи с суммой 0; unit-тест на каждую операцию ADR-0007, п. 3.
- `infrastructure/ledger.repository.ts` — `post(tx, kind, sourceId, entries)`: вставка проводки и записей, затем `account_balances` блокируются в порядке сортировки имени счёта и обновляются. Повтор той же операции ловит `UNIQUE (kind, source_id)`: проводка не создаётся, операция считается выполненной.
- Проводка всегда в одной транзакции с операцией-источником: транзакцией 2 списания, транзакцией 1 возврата и так далее (п. 5).

## 4. Комиссия

- `commission_rates` (ADR-0007, п. 4) и read-model `categories (category_id uuid PK, parent_id, name)`.
- `commissionFor(lines, rates)` — чистая функция: ставка самой глубокой категории пути с заданной ставкой, иначе `*`; `floor` по позиции через `mulBp` из `libs/contracts/money`.
- Seed: категории из fixtures; ставки — `*` = 10%, «Телефоны» = 5% (решение 3).
- API админа (`@AdminScope()`):

| Запрос                                  | Что делает                                                                   |
| --------------------------------------- | ---------------------------------------------------------------------------- |
| `GET /admin/commission-rates`           | Все ставки                                                                   |
| `PUT /admin/commission-rates/:categoryId` | Ставка в б. п. (0…10 000); неизвестная категория — `404`; `*` — по умолчанию |
| `GET /admin/reports/commission?from&to` | Заработанная и отложенная комиссия, возвраты и выплаты за период             |
| `GET /admin/ledger/check`               | Результат сверки инвариантов (п. 7) прямо сейчас                              |

## 5. Операции в коде payment

| Операция ADR-0007, п. 3      | Где                                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 1. Списание                  | Транзакция 2 `CapturePayment`: ставки фиксируются, `settlements` и `settlement_lines` по под-заказам, проводка по каждому под-заказу |
| 2. Конец удержания           | Планировщик: созревшие `HOLD` (`FOR UPDATE SKIP LOCKED`) → `AVAILABLE`                                       |
| 3. Возврат запрошен          | Транзакция 1 `RefundPayment`: расчёт `PENDING` → `REFUNDED`                                                    |
| 4. Возврат подтверждён       | Транзакция 2 `RefundPayment`: ответ провайдера на возврат (решение 1)                                         |
| 5–7. Выплата                 | п. 6                                                                                                          |

- `sub-order.delivered` (новый потребитель `order.events`): расчёт `PENDING` → `HOLD`, `release_at = occurredAt + SELLER_HOLD_MS` (7 дней; в e2e — секунды).
- Разбивка из `CapturePayment` сохраняется в транзакции 1 уже сейчас (`payment_sub_orders`); добавляются позиции с `categoryPath` — по ним считается комиссия в транзакции 2.
- Отказ провайдера в возврате (`FAILED`) — обратная проводка `refund_failed`: деньги возвращаются на `pending` продавца и `commission:deferred`, расчёт — снова `PENDING`, алерт (решение 2).

## 6. Выплаты

- **Запрос** `POST /seller/payouts { amount }` (`@SellerScope('finance')`): одна транзакция — блокировка строки баланса `seller:{id}:available`, проверки «хватает» и «не меньше `MIN_PAYOUT_MINOR`», выплата `REQUESTED`, проводка 5. Не хватает — `409`, меньше минимума — `422`.
- **Отправка** — фоновый обработчик в три шага, как вызовы провайдера в SD-02, п. 6.2: `REQUESTED` → `SENDING` → `POST /v1/payouts` с ключом `payoutId` → `SENT`.
- **Webhook** `payout.paid` / `payout.failed` через тот же `POST /webhooks/psp`: проводка 6 или 7, статус `PAID` / `FAILED`, событие `payout.paid` / `payout.failed` (`payment.events`, ключ `payoutId`).
- **fake-psp:** `POST /v1/payouts { merchantReference, sellerId, amountMinor }` + `Idempotency-Key`; через `PSP_PAYOUT_DELAY_MS` присылает `payout.paid`. Тестовое API: `POST /test/settings { failPayouts }` — следующие выплаты отказывают (`payout.failed`), `GET /test/payouts/:id`.

## 7. Сверка

- **Инварианты журнала** (ADR-0007, п. 7): задача раз в `RECONCILE_INTERVAL_MS` (сутки) и `GET /admin/ledger/check`. Расхождение — `error` с `alert: true`.
- **Сверка с erp** (критерий этапа): `GET /seller/finance/summary` в payment — сумма `S` расчётов продавца без `REFUNDED`; `GET /seller/sales/summary` в erp — продажи без сторно. E2E сравнивает их для каждого продавца. Синхронной связи payment → erp нет: сверяет наблюдатель (решение 4).

## 8. API продавца

Через gateway, `@SellerScope('finance')`:

| Запрос                              | Что возвращает                                                                  |
| ----------------------------------- | ------------------------------------------------------------------------------- |
| `GET /seller/finance/balance`       | «В ожидании», «доступно», «в выплате»                                           |
| `GET /seller/finance/operations`    | Записи журнала по счетам продавца с типом операции и под-заказом, курсор         |
| `GET /seller/finance/summary`       | Сумма `S` действующих расчётов — для сверки с erp                               |
| `GET /seller/payouts`, `POST /seller/payouts` | Выплаты продавца; запрос выплаты                                       |

## 9. Тестирование

| Уровень                         | Что                                                                                                                                                                       |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit                            | Комиссия и округление; каждая операция п. 3 ADR-0007 — сбалансированная проводка; переходы расчёта и выплаты; `@AdminScope`                                                 |
| Property-based (`fast-check`)   | Случайная последовательность операций сохраняет инварианты ADR-0007, п. 7                                                                                                |
| Интеграционные (Testcontainers) | Повтор `CapturePayment` — одна проводка; два одновременных запроса выплаты — проходит один; `UPDATE`/`DELETE` журнала и несбалансированная проводка отклоняются базой; удержание по `occurredAt`; отказ провайдера в возврате — обратная проводка |
| E2E                             | Сценарии п. 1                                                                                                                                                             |

## 10. Решения (согласовано)

1. **Возврат подтверждается ответом провайдера, без отдельного webhook.** fake-psp отвечает на `refund` сразу итогом, как на `capture`. Поэтому проводка 3 пишется в транзакции 1 возврата, проводка 4 — в транзакции 2. Счёт `refunds:in-transit` остаётся: он ненулевой ровно между ними. _Альтернатива:_ асинхронный возврат с webhook — ещё одна ветка в fake-psp и payment без новой проверки для критерия этапа.
2. **Отказ провайдера в возврате — обратная проводка `refund_failed`** (не предусмотрена ADR-0007): деньги возвращаются на счета продавца и комиссии, расчёт — снова `PENDING`, алерт. Иначе сумма зависла бы на `refunds:in-transit`. ADR-0007 дополняется.
3. **Категории до этапа 5 — seed в payment**, ставки по умолчанию: `*` = 10%, «Телефоны» = 5%. На этапе 5 read-model наполнят события `category.*`, а API ставок уже проверяет категорию по нему.
4. **Сверка с erp — наблюдателем (e2e и, позже, админка), а не вызовом payment → erp.** Сервисы не зависят друг от друга синхронно ради отчёта (ADR-0001, п. 3).
5. **Минимальная сумма выплаты — 100 000 сум** (`MIN_PAYOUT_MINOR = 10 000 000`), срок удержания — 7 дней (`SELLER_HOLD_MS`). Оба значения — открытые вопросы ТЗ (раздел 10); это значения по умолчанию в env.
6. **Расчёты по уже списанным до этапа 4 заказам не создаются.** Боевых данных нет, стенды пересоздаются; миграция данных не нужна.

## 11. Порядок работ

1. Контракты `payout.*`; `libs/auth`: `@AdminScope()`.
2. payment: журнал (миграция с триггерами, `domain/ledger`, репозиторий), unit и property-based тесты.
3. payment: комиссия, расчёты, проводки списания и возврата, удержание по `sub-order.delivered`; интеграционные тесты.
4. fake-psp и payment: выплаты, webhook, API продавца и админа, сверка.
5. erp: сводка продаж; gateway: маршруты.
6. e2e: сценарии п. 1.
7. CHANGELOG, SD-04 → «Реализовано», ТЗ: этап 4 ✅, ADR-0007 (решение 2, `uuid`), SD-00.
